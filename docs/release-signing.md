# Release-signing key provenance

`jankurai-installer.sh` verifies every release from `v1.7.2` on against one
pinned release-signing key. This page records where that pin comes from, so a
reviewer can check it instead of taking it on trust.

## The pin

```text
jankurai-release-2026.pub|99f48af11e4e6463544652ddfaefb0e9953de15fb0802b174123ac2907ff06fc|v1.7.2|
```

Each `release_keys` line is `name|sha256|first tag|last tag`. The installer
downloads the key file with the release and refuses it unless its SHA-256
equals the pin. It then verifies the asset's cosign bundle against that key.

## Where the key comes from

1. **Generated by the owner.** The owner created the key pair on the signing
   host with the hub's `ops/release/generate-signing-key.sh`. The private key
   lives outside every Git repository, in a mode-600 file under a mode-700
   directory, protected by a password cosign prompts for. It is never
   committed, never put in CI, never given to an agent, and never copied to a
   host that does not sign. `ops/release/sign-release.sh` in the hub refuses to
   sign with a key whose public half is not the one the installer pins.
2. **Public half committed in the hub.** The public key was committed as
   `release-keys/jankurai-release-2026.pub` in hub PR root/jankurai #11, merged
   as `cf5e0c8b078a978a5396af329460a116d7acc08b`. That file's SHA-256 is
   `99f48af11e4e6463544652ddfaefb0e9953de15fb0802b174123ac2907ff06fc`.
3. **Pinned by the hub installer** in the same commit, with a valid-from of
   `v1.7.2`.
4. **Used for a release.** `v1.7.2` was published key-signed with this key and
   verified against this pin with the pinned cosign `v3.1.3`. For example, the
   Linux x86-64 asset `jankurai-1.7.2-x86_64-unknown-linux-gnu.tar.gz` has
   SHA-256 `aac2b6b6ae77766d6246e3ccea045541dd50a3ae0285714eb5c8bc20a6c78c30`,
   and its signed provenance names source commit `ff6e03d7`.

## How this repository holds it

This repository vendors the hub's key file byte-for-byte as
`agent/vendor/release-keys/jankurai-release-2026.pub`.
`agent/vendor/hub-installer.lock` records:

- the key's hub path, source commit (`cf5e0c8`), SHA-256 and first tag;
- the installer's whole `release_keys` table, line for line
  (`release_signers_table`).

`scripts/check-vendored-installer.sh` runs in the required lane
(`bash scripts/ci-local.sh required`, which `ops/ci/pr-ci.sh` runs). It makes
two kinds of check.

**Self-consistency.** It refuses:

- any installer `release_keys` line that is not in the lock's table. This
  covers an added key, a closed or moved range, and a changed hash.
- any pinned key that is not vendored with exactly its pinned SHA-256.
- any vendored key that no line pins (names compared as fixed strings).
- a current key that is not open-ended from its first tag.

These only prove the files here agree with each other. A coherent swap, where
the key file, the lock and the installer pin are all replaced with a new key
together, passes all of them.

**The hub comparison, mandatory.** It then requires the installer to be
byte-identical to the hub's `jankurai-installer.sh` at the lock's
`source_commit`, the current key to be byte-identical to the hub's
`release-keys/jankurai-release-2026.pub` at `release_signer_source_commit`, and
every vendored key to be the hub's file at `source_commit`. Both commits must
be on the hub's `main` branch; a commit on any other hub ref does not count. The
installer and every vendored key must also equal the hub's **current** files at
the tip of `main`. Ancestry alone would let this repository keep an older pin
after the hub revoked a key; with the currency check, a hub change to the
installer or a key fails this lane until the repository re-syncs.
`scripts/hub-source.sh` finds the hub. Which repository is the hub is fixed
there in code (`HUB_REPO=root/jankurai`), not read from the lock: the lock's
`source_repo` must equal it, or the check fails. In the required lane the hub is
the sibling `../jankurai`, used only when its origin is the hub URL derived from
this checkout's origin (its `main` is `origin/main` only, never a local branch),
or else a fresh clone of that derived URL. That derivation only happens when
origin is `<base>/root/jankurai-deploy` or the scp-like
`<user@host>:root/jankurai-deploy`, and gives `root/jankurai` in the same form.
The clone never prompts for credentials and gives up after 300 s. Any other origin, such as a GitHub mirror
under another owner whose old hub name could be claimed by someone else,
derives nothing and the check fails. Both are set by
whoever runs the lane, never by a pull request: `ops/ci/required.sh` unsets
`JANKURAI_HUB` and `JANKURAI_HUB_URL`, which a person running the check by hand
may use to name a hub checkout or URL. If no hub holds both commits on `main`,
the check fails. It does not pass with a note.

The one opt-out is `JANKURAI_HUB_CHECK=local-dev-skip`, for offline local
development. It prints that the comparison was skipped. `ops/ci/required.sh`
unsets it, so it cannot make the required lane pass.

`.github/workflows/ci.yml` is still committed, but it is inert: GitHub is
publish-only for this family and GitHub Actions is disabled on the mirror, so
the workflow never runs; its removal is tracked separately. If it ever did run,
its origin would be under the GitHub owner, so it would derive no hub URL and
fail at this step: the comparison failing closed. The required lane counts on
the forge gate, where the hub is the composed sibling `../jankurai`.

`scripts/check-vendored-installer-test.sh`, in the same lane, shows each of
these refusals happen. It includes a coherent swap to a freshly generated key,
refused only because it does not match the hub. It also shows that the same
swap committed on a hub side branch is refused, and that the check fails when
the hub is unavailable or does not hold the locked commits.

What this proves, and what it does not: it binds this repository's installer
and keys to whatever the hub's `main` branch holds at those commits. It does
not prove who generated the key. That rests on the hub's review of root/jankurai
PR #11 and on the owner's custody of the private key, described above.

The hub's `scripts/validate-family.mjs` (`vendored-trust.mjs`) runs a second,
independent comparison: on a composed family checkout it compares every
member's vendored installer and release keys with the hub's own files.

To check the chain against the hub yourself:

```bash
sha256sum agent/vendor/release-keys/jankurai-release-2026.pub
git -C <hub checkout> show cf5e0c8b078a978a5396af329460a116d7acc08b:release-keys/jankurai-release-2026.pub | sha256sum
JANKURAI_HUB=<hub checkout> bash scripts/check-vendored-installer.sh
```

## The open-ended range, and the owner's decision to close it

The pin's last tag is empty: the key covers `v1.7.2` and every later tag until
it is rotated. The argument for that was that one key signs every release until
the owner rotates it, so pinning a closing tag ahead of time would make the next
release unverifiable.

The owner has since ruled the other way: a release-key pin must cover exactly
the releases it signs, not an open-ended range, so a release nobody has reviewed
the pin for fails closed instead of inheriting trust. The key has signed
`v1.7.2`, `v1.7.3`, `v1.7.4` and `v1.7.5`, so its line should end `|v1.7.5` and
be extended by a reviewed change for each later release.

That change cannot land here. `jankurai-installer.sh` in this repository is the
hub's file byte for byte, and the required lane proves it against the hub's
`main` (above); closing the range here would be a hand-edit of vendored trust
material and the lane would, correctly, refuse it. The range is closed in the
hub's `jankurai-installer.sh` first, and this repository then follows with
`bash scripts/sync-hub-installer.sh <hub checkout>` — the same path as a
rotation. `scripts/check-vendored-installer.sh` currently requires the current
key's line to be open-ended from its first tag; that expectation moves to "ends
at the last release the key signed" in the same sync.

`neverhuman/jankurai-action` does not vendor the hub installer, so its own copy
already pins the bounded range `v1.7.2|v1.7.5`.

## Rotation and revocation

- **Rotation** lands in the hub first. A PR commits the new public key under
  `release-keys/`, closes the old key's range in the installer's
  `release_keys` table (sets its last tag), and appends the new key with its
  first tag. Old releases keep verifying under the old key.
- **This repository follows** with `bash scripts/sync-hub-installer.sh <hub
  checkout>`. That copies the installer and every pinned key file, removes
  vendored keys the table no longer pins, and updates the lock,
  so the rotation shows up here as a diff of the key file, the lock and the
  installer.
- **Revocation**: ship an installer whose table no longer accepts the key for
  the affected tags, then re-sign or withdraw those tags.

## No transparency log or build attestation, by design

Key-signed releases are built and signed on our own hosts. GitHub only
publishes them. Verification is offline (`--insecure-ignore-tlog=true
--offline=true`), and there is no Rekor entry or GitHub build attestation on
this path. A log entry would add third-party evidence of *when* a signature was
made, but not of *who* made it: that trust rests on custody of the pinned key
either way.

What verification proves: the asset is byte-for-byte what the holder of the
pinned key signed. Its signed provenance names the tag, source commit and tree.
Builds are reproducible from that source.

A compromised key could sign assets the installer accepts, until an installer
that no longer trusts it ships. The hub's `SECURITY.md` says how to report a
suspected compromise.
